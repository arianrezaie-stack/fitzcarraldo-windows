I traced the renderer → preload → Electron main → native engine path, and we now have the actual root cause.

The protocol mismatch is here

Your native engine says the protocol is one JSON object per line.

But native-engine/src/main.cpp currently serializes JSON like this:

std::cout << juce::JSON::toString(event, false).toStdString() << '\n' << std::flush;

at line 1118 in the current source.

That false is the problem.

Your manual test proved it: the engine returned:

{
  "type": "error",
  "code": "ENGINE_ERROR",
  "message": "unknown command"
}

That's pretty-printed multi-line JSON.

But Electron's main.cjs deliberately treats each newline as the end of one JSON message:

const line = stdoutBuffer.slice(0, newline).replace(/\r$/, '');
...
if (line) handleEngineLine(line);

and then does:

event = JSON.parse(line);

at lines 901–907 and 829–837.

So Electron receives:

{

and immediately tries:

JSON.parse('{')

which fails.

That is exactly your “engine sent invalid JSON” error.

Exact changes
1. Native engine — REQUIRED

File:

artifacts/werfeed-herzback/native-engine/src/main.cpp

Current line 1118:

std::cout << juce::JSON::toString(event, false).toStdString() << '\n' << std::flush;

Change it to:

std::cout << juce::JSON::toString(event, true).toStdString() << '\n' << std::flush;

That's the primary fix.

The resulting output becomes one physical line:

{"type":"error","code":"ENGINE_ERROR","message":"unknown command"}

which is exactly what Electron's line parser expects.

The engine already has the correct newline framing; only the JSON formatting flag is wrong.

2. Electron main — REQUIRED lifecycle fix

There's a second bug that explains why the UI can remain in a strange/uninitialized state.

In:

artifacts/werfeed-herzback/electron/main.cjs

the application currently does:

app.whenReady().then(() => {
  startEngine();
  createWindow();
});

at lines 1095–1099.

That means:

engine starts
engine immediately emits hello
broadcast() looks for BrowserWindows
there isn't one yet
hello disappears
only afterward does Electron create the window

broadcast() explicitly sends only to existing windows.

Change the order to:

app.whenReady().then(() => {
  createWindow();
  startEngine();
});

This isn't the cause of the malformed JSON, but it is a genuine startup race and should be fixed in the same build.

3. Electron main — strongly recommended diagnostic improvement

Still in:

artifacts/werfeed-herzback/electron/main.cjs

the parser currently hides the offending data:

try {
  event = JSON.parse(line);
} catch {
  protocolError('Engine sent invalid JSON.');
  return;
}

at approximately 829–839.

Change it temporarily to:

try {
  event = JSON.parse(line);
} catch (error) {
  console.error('[werfeed engine] invalid JSON:', JSON.stringify(line));
  protocolError(`Engine sent invalid JSON: ${JSON.stringify(line.slice(0, 500))}`);
  return;
}

I would actually keep this diagnostic logging in the development build, because if the native protocol ever regresses again, you'll immediately see the actual bytes/line Electron received.

4. Preload — DON'T CHANGE IT

I traced preload.cjs.

It correctly exposes:

window.werfeedDesktop.engine

and validates exactly the six native commands:

list_devices
configure
start
stop
set_protection
start_calibration

It then forwards them through:

ipcRenderer.invoke('werfeed-engine:command', command, payload)

at lines 347–368.

No protocol change is needed here.

5. React renderer — DON'T CHANGE THE command protocol

App.tsx is also using the correct bridge.

The important section is around 626–683:

subscribes to engine events
handles hello
handles devices
handles state
handles telemetry
calls list_devices once the engine is running.

Then the Start button sends:

bridge.command('configure', {
  deviceType: selectedPair.input.deviceType,
  inputDevice: selectedPair.input.name,
  outputDevice: selectedPair.output.name,
  ...
})

around 687–701.

So the renderer's command names match the native protocol.

The UI disabling is also intentional:

const nativeReady = !!bridge && engineStatus.state === 'running';

and the Start button is disabled when nativeReady is false.

That explains your observation that the buttons won't become usable: if the engine startup/event state isn't reaching the renderer correctly, nativeReady never becomes true.

6. Type declaration — no change required

src/werfeed-desktop.d.ts already declares the same six commands and the event/status APIs.

Why I'm confident this is the root cause

Your three pieces of evidence line up perfectly:

Native engine manual output: multi-line JSON.

Electron: splits stdout at every newline and parses each piece independently.

Electron error: therefore reports Engine sent invalid JSON.

And the native source explicitly shows the formatting flag that produces the multi-line output.

So don't rewrite the IPC layer, don't replace the preload, and don't switch audio APIs yet. Fix the single false → true first, rebuild the engine, package it, and then test device enumeration.
